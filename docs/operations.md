# Эксплуатация

## Очередь и наблюдаемость

Webhook проверяет секрет и транзакционно сохраняет update_id + задание. Квитанция и подтверждение оплаты сохраняются до обращения к Telegram. Уникальные ключи заданий предотвращают повторную постановку. Worker использует PostgreSQL SKIP LOCKED и lease на 5 минут, повторные попытки с задержкой, Telegram retry_after и предел 8 попыток. После лимита задача видна со статусом failed. Сообщения в Telegram имеют семантику **at least once**: если Telegram принял сообщение, а процесс упал до записи done, повторная доставка возможна. Exactly-once для внешнего Telegram API не обещается. Полезные действия в БД (оплата, доступ, регистрация) повторобезопасны.

Длинные рассылки разбиваются на страницы по 100 пользователей и отдельные задания. Worker обрабатывает максимум 20 задач/45 секунд за cron. Для большой аудитории увеличивайте частоту/число защищённых worker, следя за лимитами Telegram. Текущий MVP сериализует короткие транзакции бизнес-записей общей advisory-блокировкой. Это обеспечивает согласованность лимитов/доступа, но до масштабирования стоит перейти на блокировки по пользователю/событию с нагрузочным тестированием.

Не запускайте Telegram polling. После восстановления машины процессы сервера и планировщика надо запустить заново. Очередь сохраняется в PostgreSQL. При изменении бота/токена задайте webhook повторно. Старые зависшие задачи автоматически подхватятся после lease. При ошибках интеграции устраните причину, затем вручную переведите конкретную failed-задачу в pending и обнулите attempts через защищённый SQL-сеанс. Не сбрасывайте все задания целиком и не удаляйте paid/outbox записи.

На Hobby защищённый GET /api/cron вызывается внешним планировщиком раз в минуту. Маршрут возвращает HTTP 200 {"accepted":true}, после чего Next.js after() выполняет работу в рамках лимита функции 60 секунд. Ответ {"busy":true} означает, что предыдущий запуск ещё удерживает lease. Lease живёт 65 секунд и освобождается только владельцем; после аварийного завершения новый запуск подхватит работу после истечения lease. HTTP 200 подтверждает приём, а не доставку сообщений. Владелец видит последний результат в Настройки → schedulerStatus: время начала/завершения, status, done и failed. При status=completed_with_failures проверьте очередь; при status=error — соединение с БД и серверные логи. Если функция принудительно остановлена по времени, запись статуса может не обновиться — проверяйте её свежесть и логи. Задания сохраняются в PostgreSQL.

Health endpoint проверяет соединение БД; он не доказывает работоспособность бота. Реальная приёмка требует сообщений в staging-боте, подтверждения платежа, входа в группу и проверки cron. Sentry подключается только при заданном DSN; подключение в текущей среде не проверено. Сырые payload update, квитанции и заявки не следует направлять в логи/Sentry. Платформа мониторинга и alerting на failed-задачи требуют отдельного подключения.

## Резервные копии

Перед production включите Neon PITR/историю восстановления по тарифу, ограничьте роли доступа и задайте срок хранения. Дополнительно выполняйте `pg_dump --format=custom --file=/secure/location/maksim.dump "$DIRECT_URL"` в доверенной инфраструктуре с зашифрованным хранилищем, ограниченным доступом и lifecycle. Не выводите строку подключения. Рекомендуемая начальная политика: ежедневные копии на 30 дней с согласованием юридических требований владельцем.

Проверяйте восстановление на отдельной staging-базе: `pg_restore --no-owner --no-acl --dbname="$RESTORE_DATABASE_URL" /secure/location/maksim.dump`, затем проверьте миграции, суммы заказов, количество доступов, регистрации, очередь и health. При восстановлении не подключайте production-бота, не запускайте рассылки или cron до ревизии очереди. Сохраняйте журнал времени копирования/восстановления и результатов. Реальный Neon PITR и восстановление из production-копии в этой среде не проверены.

## Данные и квитанции

Telegram file_id — ссылка на файл в Telegram, а не независимая резервная копия. Нужна утверждённая политика хранения квитанций и при необходимости отдельное защищённое архивирование. Веб-загрузка идёт через авторизованный сервер и отдаётся как attachment. Не сохраняйте квитанции в публичный Blob.

До запуска владелец должен утвердить политику обработки данных, сроки хранения и порядок запросов удаления. По запросу сначала отзовите доступ и согласие, прекратите ожидающие marketing-задачи, затем анонимизируйте профиль/обращения и удалите связанные аналитические payload/update в защищённой БД, сохранив только те финансовые записи, которые необходимы по закону. Автоматизированное полное удаление персональных данных и очистка старых receipt/update пока не реализованы; операции выполняет ответственный администратор по согласованной процедуре. Консультации хранят только краткую заявку, бот предупреждает не присылать медицинские сведения.

Локальная проверка резервирования: `bash scripts/backup-smoke.sh` создаёт dump фиксированного локального контейнера, восстанавливает его в отдельную disposable базу, сравнивает схему/выбранные количества записей и удаляет только созданную проверочную базу. Успешно выполнена; production-резервирование этим не подтверждается.
