# Развёртывание

Node.js 22.12+ (проверено с 24), npm, PostgreSQL 17. Код рассчитан на Next.js / Vercel, webhook вместо polling. Каталог проекта — корень этого репозитория.

## Локальная разработка

1. `npm ci` (при недоступном домашнем каталоге: `npm_config_cache=/workspace/.npm-cache npm ci`).
2. Скопируйте `.env.example` в `.env`, сохраните существующий файл, если он уже есть. Введите собственные значения локально, не коммитьте их.
3. Для локальной БД можно использовать `compose.yaml`: `docker compose up -d`.
4. `npm run db:generate`.
5. Для нового disposable PostgreSQL на localhost: `npm run db:local`. Скрипт применяет SQL начальной Prisma-миграции транзакционно и не является заменой production-миграций. Повторный запуск не изменяет уже созданную схему. Для последующих изменений схемы используйте новые миграции, а не этот bootstrap.
6. `npm run db:seed` — добавляет тексты и выключенные шаблоны сценариев, не перезаписывает настройки и не создаёт фиктивные продажи/аудио.
7. `npm run dev`. `GET /api/health` должен вернуть `{"status":"ok"}`.
8. `npm run worker` обрабатывает один пакет очереди и завершает работу. Для локальной разработки запускайте повторно планировщиком. Production использует защищённый cron.

`db:generate` использует официальный WASM-компилятор, включённый в пакет Prisma; клиент работает через стабильный JS driver adapter PostgreSQL. `scripts/prisma-wasm.config.ts` — экспериментальная альтернативная конфигурация CLI для генерации клиента/SQL в ограниченной сети. Production deploy её не использует: `npm run db:deploy` вызывает стандартный Prisma migrate deploy с проверкой контрольных сумм бинарных компонентов. Для этого нужен доступ к `binaries.prisma.sh`. Миграцию можно сгенерировать через WASM, но её применение через WASM в этой среде не прошло из-за несовместимости типа PostgreSQL `name`; для локального тестирования использован SQL bootstrap.

## Переменные

| Имя | Назначение |
| --- | --- |
| DATABASE_URL | Neon pooled PostgreSQL URL; TLS `sslmode=require`, выдайте приложению минимальные права |
| DIRECT_URL | Direct URL той же базы для миграций; отдельные повышенные права для deploy |
| BOT_TOKEN | Токен BotFather, нужен и Bot API, и локальному вычислению подписи Telegram Login |
| NEXT_PUBLIC_BOT_USERNAME | Публичное имя бота без `@` |
| OWNER_TELEGRAM_IDS | Telegram ID владельца, через запятую; обязательны для первоначального входа |
| AUTH_SECRET | Случайный секрет сессий, минимум 32 символа |
| WEBHOOK_SECRET | Случайный секрет webhook, допустимы A–Z a–z 0–9 _ -, максимум 256 символов |
| CRON_SECRET | Случайный секрет Vercel Cron |
| APP_URL | HTTPS production origin без завершающего `/` |
| COMMUNITY_CHAT_ID | Числовой ID закрытой supergroup, обычно начинается с -100 |
| PAYMENT_DETAILS | Банковские реквизиты; доступны только серверу и покупателю при создании заказа |
| PUBLIC_CHANNEL_URL | Ссылка на открытый канал |
| SENTRY_DSN | Необязательно: мониторинг ошибок сервера |
| TEST_DATABASE_URL | Только локально/CI: отдельная disposable база, имя заканчивается на `_test` |

Секреты вводятся через защищённые настройки проекта, а не в чат. BOT_TOKEN должен быть настоящим серверным значением: proxy placeholder недостаточен для проверки HMAC Telegram Login. DATABASE_URL и DIRECT_URL также должны быть доступны процессу для PostgreSQL, а не только HTTPS-прокси. Не выводите переменные и строки подключения в логи.

## Neon / Vercel / Telegram

1. Создайте Neon через Marketplace Vercel, проверьте pooled/direct URL. Настройте backup/PITR по доступному тарифу, прежде чем принимать реальные платежи.
2. Подключите репозиторий в Vercel; framework Next.js, build `npm run build`. Задайте production-переменные; для preview используйте отдельную БД и отдельного бота.
3. В release job выполните `npm ci`, `npm run db:generate`, затем `npm run db:deploy`. Не запускайте миграции параллельно из нескольких preview-сборок. После миграции один раз выполните `npm run db:seed`.
4. В BotFather задайте `/setdomain` для Telegram Login — домен APP_URL. Назначьте бота администратором закрытой supergroup с правами приглашения, одобрения заявок и блокировки участников. Удалите общедоступные постоянные приглашения, иначе вступление возможно вне платного сценария.
5. После deploy выполните `npm run telegram:webhook` с production-переменными. Скрипт не удаляет ожидающие updates. Он отправляет реальную команду настройки боту; запускать только для своего бота.
6. Убедитесь, что тариф Vercel поддерживает cron каждую минуту и 60 секунд выполнения. На тарифе с ежедневным cron этот workflow не готов: нужен подходящий тариф либо внешний защищённый планировщик с `Authorization: Bearer CRON_SECRET`.
7. Настройте команды `/start`, `/subscribe`, `/unsubscribe`, `/privacy`, `/cancel` через BotFather. Войдите в `/admin` как владелец и добавьте реальные материалы.
8. Пройдите [приёмку](acceptance.md) на staging, затем на production с контролируемой покупкой.

Сетевые назначения: npm registry, `binaries.prisma.sh`, `api.telegram.org`, `telegram.org`, ваш hostname Neon, Sentry ingest hostname (если подключён). Allowlist среды Codex и сеть production Vercel — разные настройки.

## Telegram и цифровые товары

Банковское подтверждение реализовано по ТЗ. До запуска продаж цифрового контента внутри Telegram требуется проверить действующие правила Telegram: для таких товаров Telegram требует Stars. Текущий адаптер ручной оплаты не реализует Stars и сам по себе не подтверждает допустимость банковских продаж в боте. Для production цифровых продаж потребуется отдельный адаптер Stars/согласованный допустимый сценарий. Код не имитирует оплату и не отмечает квитанцию доказательством поступления денег.
